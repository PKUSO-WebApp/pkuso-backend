# MCP 操作审计日志（历史目录）

⚠️ **本目录是历史记录，不是现行的流程。** 现在数据库变更**一律**走 migration：
写在 `supabase/migrations/` → PR → 合并到 `main`（CI 自动应用到 dev）→ 需要时手动触发 prod。
MCP 只用于**只读**排查。所以正常情况下这里不会再有新文件。

目录里那两份（`2026-09-07_*`、`2026-09-22_*`）记录的是当年「直接在库上改、事后补一份说明」
的做法。那种做法的代价后来显现了：**仓库里没有对应的 SQL**，于是 dev 与 prod 的 schema 各自
漂移，而仓库再也说不清线上到底是什么样（本仓 18 个 stub 占位文件是同一病根的另一半）。

## 万一又走了那条路

真到了只能直接改库的紧急情况（那时请先想清楚：为什么 CI 这条路当下走不通），
**仍然**在此补一份记录，格式见下 —— 但更重要的是**同时补一个 migration**，
让仓库能重建出那个状态；补不上就说明这次改动不该留在库里。

## 为什么删掉了 `audit-check.yml`

它本来负责在 PR 阶段检查「有没有 MCP 操作没配审计文件」。删掉的原因是：
**它的唯一 `exit 1` 要求 `audit/` 下没有任何 md 文件**，而那个目录恒有两个历史文件
⇒ 结构性不可能失败，却以「Audit Check」的名字在 PR 上显示绿勾。

取而代之的是 `scripts/check-migrations.mjs`（进了闸门，CI 与人调的是同一条）：
它检查的是**真的会出问题、且机器可判定**的四件事 —— 命名格式、版本号重复、
新增的 stub 占位、以及**有没有改/删已提交的 migration**。

## 文件命名

`YYYY-MM-DD_<简述>.md`

示例：`2026-09-07_fix_profiles_select_grants.md`

## 文件格式

```markdown
# MCP 操作记录

- **时间**: YYYY-MM-DD HH:MM
- **操作者**: agent / 人工
- **环境**: dev / prod
- **操作类型**: apply_migration / execute_sql / deploy_edge_function / 其他

## 操作内容

（实际执行的 SQL 或操作描述）

## 目的

（为什么要做这个操作）

## 影响

- 涉及表:
- 涉及 RLS:
- 涉及 Edge Functions:

## 后续

- [ ] 需要在 migrations/ 中补充正式迁移文件
- [ ] 需要更新两端 database.types.ts
```

## CI 检查

无。（原来写在这里的「`audit-check.yml` 会在 PR 时检查审计文件的完整性，CI 会失败」是一句
**不成立的话** —— 见上一节。）
